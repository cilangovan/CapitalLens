# CapitalLens multi-tenant schema (phase 1)

Prototype of the SaaS data model from the CapitalLens SaaS Plan. It lives in a **separate Supabase
project** (`capitallens-demo`), not the live single-user database, and is not wired to the dashboard yet.

| File | What it does |
| --- | --- |
| `01_schema.sql` | Tenant tables (`user_id` on every row), shared market tables, `profiles`, `broker_connections`, `broker_secrets`, `sync_jobs`, row-level security, grants, sign-up trigger |
| `02_seed_demo.sql` | `seed_demo_portfolio()`: the mock broker, a year of seeded Trading 212-shaped data for one user |
| `03_rls_isolation_test.sql` | `rls_isolation_test()`: 63 checks that users see only their own rows |

## Rebuild the demo

1. Create an empty Supabase project and run the three files in order (SQL editor or `psql`).
2. Create two users (Authentication, Users, or the sign-up API): `demo@capitallens.test` and
   `demo-b@capitallens.test`. The trigger in `01_schema.sql` creates their profiles.
3. Seed them:
   ```sql
   select public.seed_demo_portfolio((select id from auth.users where email = 'demo@capitallens.test'), 0.42, 1, null);
   select public.seed_demo_portfolio((select id from auth.users where email = 'demo-b@capitallens.test'), 0.77, 0.3, array['VWCEd','VUSAa','SGLNl','AAPL']);
   ```
4. Check isolation: `select public.rls_isolation_test();` should return `"all_pass": true`.

## Design notes

- Users can only **read** their own rows. They may also mark their alerts read/dismissed/archived,
  manage their watchlist, and edit their profile. Everything else is written by the service role.
- `broker_secrets` (encrypted keys) and `sync_jobs` have RLS on and no policy: service role only.
- Not yet covered: archive tables, `app_settings`, `dashboard_auth` (replaced by Supabase Auth),
  realised P&L (the mock broker only places buys), and the Python sync services (still single-user).
- Mock data is synthetic. Pie names and tickers mirror the owner's structure; weights, prices and
  amounts are invented. The seeded random walk is reproducible for a given Postgres version.

## Demo dashboard

`docs/demo/` is a copy of the dashboard that signs in with Supabase Auth and reads the demo project
directly (row-level security does the scoping). It reuses the real `docs/js/*` files; only
`demo-auth.js` (login) and `demo-shim.js` (data access) differ. Served at
`https://cilangovan.github.io/CapitalLens/demo/`. Search, charts, watchlist edits and settings need
the worker and are switched off in the demo. `portfolio_snapshots_all` / `positions_all` views are
added to the demo project because the dashboard reads them.

## Phase 2: self-service Trading 212 connect

- `docs/app/` is the multi-user app (generated by `python3 scripts/build_app.py` from the dashboard in `docs/`): email sign-up and
  sign-in via Supabase Auth, an Accounts tab with the connect wizard, sync status and disconnect.
- `supabase/functions/broker/index.ts` is the Edge Function. `POST /connect` validates a Trading 212 key (live or practice),
  stores it in Supabase Vault and queues a sync. `POST /tick` (called every minute by pg_cron with a shared secret) runs due
  jobs: a portfolio snapshot every 15 minutes, and a paced walk of orders, dividends and transactions (4 pages per tick).
- `05_broker_connect.sql` has the database side. Credentials never leave the function and are never returned to the browser.
- Not yet: password reset, per-user alerts/analytics (phase 3), Zerodha (phase 4).

## Phase 3: original project converted to multi-user (production)

`06_convert_legacy.sql` was applied to the original `t212` project in place (owner id substituted for `:OWNER`), then `05_broker_connect.sql`
with that project's ref. A full copy of every table taken beforehand is in the private `legacy_backup` schema.
Backwards compatible: the GitHub Actions pipeline and the Cloudflare worker are unchanged. Their inserts get `user_id` from a column
default (the owner), and the old single-column unique keys stay next to the new per-user ones until cutover.
Cutover still to do: per-user alerts and analytics, drop the old unique keys, retire the single-user worker.
Until cutover the owner must not connect Trading 212 in the app, or snapshots would be written twice (legacy pipeline and new sync).
